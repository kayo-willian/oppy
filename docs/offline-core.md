# Offline collections and notification delivery

[Português (Brasil)](../pt-BR/docs/offline-core.md) · [Home](../README.md)

Call `record_collection(path, listing, details, observed_at=...)` with a parsed listing and one detail result for each listed selection. The optional observation time must include a UTC offset. The function reads the last valid snapshots inside a SQLite write transaction and returns the recorded outcome. The no-argument command initializes the database and exits. The run command starts the scheduler. Run `python -m oppy status` for local diagnostics.

Schema version 2 adds five tables. Collections record UTC time, outcome and reason. Selections and courses store the latest accepted snapshots. Courses use a local stable ID and retain the last observed alias and definite registration status. Events store a unique transition key and the notification payload. Each event owns one outbox row. Snapshot changes, collection history, events and pending rows commit together.

The first complete collection queues one summary with counts and titles of explicitly open courses. Later collections can announce new selections, new courses, future registration, opening, closure, full places, reopening, date corrections and new or amended documents. A new selection's payload includes its initial status. Later selection and course status transitions have separate identities. A future start time is an announcement; opening requires an observed open status. Documents are tracked by URL within a selection. Without fetching files, a replacement at the same URL with the same label is undetectable.

Failed or inconclusive inputs record only history. A missing detail or unresolved change defers the whole collection. An absent known row is retained. Exact repeats of indistinguishable observations need no writes. When a new row could be a renamed missing course, keep the previous state until identity can be resolved. Each deduplication key includes source, selection, local course ID, event type, previous and next values, and the previous state revision. The revision distinguishes genuine repeated transitions across separate close/reopen cycles.

Pass a channel with a `send(notification) -> bool` method to `deliver_pending(path, channel)`. Use one delivery worker. Each invocation attempts each pending row at most once. Failure remains pending with an attempt count, last failure time and error. A later successful retry keeps the last failure available for diagnostics. Only an explicit True marks the row sent. Delivery is **at-least-once**: interruption after acceptance and before the database commit can cause the same event ID to be delivered again. The test memory channel holds messages only for the life of the process. The Telegram channel pauses the delivery batch on a provider failure. Schema version 3 adds the source Retry-After deadline to the collection record. Incident and recovery alerts use the same transaction and outbox as course events.
